# AGENTS.md

## Project Overview

**Tabinet** is a Chrome extension (Manifest V3) that sorts and organizes browser tabs and saves/restores sets of windows and tabs as sessions. It groups tabs by hostname/domain, handles duplicate tabs, supports suspended tab detection, and keeps a local session store (saved sessions plus automatic history snapshots, on by default) with unified search, import and export, plus an optional, end-to-end encrypted cloud sync of saved sessions, memos, YouTube notes (with their screenshots) and settings (off until the person signs in with Google in Settings > Account; see "Cloud sync"). On request it also pauses every playing video in every YouTube tab ("Pause all YouTube videos", behind an optional host permission the person grants in Settings), and keeps timestamped notes on a YouTube video in Chrome's side panel ("YouTube notes", `notes-panel.html`, behind the same permission; stored locally, and synced end-to-end encrypted, one item per note, only after a sign-in; see Storage Schema and Cloud sync). Free-form memos have their own page in the app (`#memo/<id>`; stored locally, synced the same way). Everything else is entirely local: without a sign-in to sync the extension makes no network requests, and snapshots never leave the device.

- Repository: `https://github.com/thilllon/tabinet`
- Chrome Web Store: `https://chromewebstore.google.com/detail/bmbpmnfhfbdjdjpblimidmbohgccmjdg`

## Architecture

### Runtime Model

This is a **Chrome Extension** with three execution contexts:

1. **Background Service Worker** (`src/service-worker.ts`) - The core engine. Runs as a Manifest V3 service worker. It is one file and the only one the worker loads directly; it holds the event wiring and nothing else, and calls into `src/lib/`. It registers, synchronously at module top level, every listener: the icon click (`chrome.action.onClicked`), which runs `sortTabGroups()` from `src/lib/sort-tabs.ts` (sorting, grouping and duplicate detection), and the sessions listeners: `runtime.onInstalled` (recreate context menus; `sessionRepo.migrateAll()` when `details.reason === 'update'`, then `sessionRepo.reconcile()`, then `ensureHistoryAlarm()`), `runtime.onStartup` (clear badge, recreate context menus so their titles follow the current language, reconcile (sessions, notes, memos) and adopt memo drafts, `promoteRecoveredSnapshot()`, re-arm the periodic alarm, one-shot `history-first` alarm), `contextMenus.onClicked` and `commands.onCommand` (save window / save all / open dashboard / gather all windows into the focused one - `assemble-tabs`, logic in `src/lib/assemble-tabs.ts` / pause every YouTube video - `pause-youtube`, logic in `src/lib/pause-youtube.ts`), `alarms.onAlarm` (`takeHistorySnapshot({ origin: 'alarm' })`), a **second** `action.onClicked` listener (fire-and-forget `takeHistorySnapshot({ origin: 'manual' })` alongside the sort, which it never awaits or alters) and `storage.onChanged` (re-arm or clear the alarm when `sessionSettings` changes; put the new language in use and re-title the menus when `uiLanguage` changes in sync storage; adopt memo drafts when a `memoDraft:*` is written). The worker wakes only on those events - plus the cloud sync alarms while signed in to sync, and the history alarm while snapshots are enabled (the default); with snapshots off and signed out of sync no alarm exists and it wakes on user actions only. There are **no** `chrome.tabs.on*` / `chrome.windows.on*` / `chrome.tabGroups.on*` listeners in the worker.
2. **The app page** (`src/pages/`, rendered in `app.html`) - one React SPA for everything that is not the icon click; there is no separate options page since v7.2.0. `app.tsx` owns the hash route (`src/lib/app-route.ts`: `#open`, `#saved/<id>`, `#auto/<id>`, `#notes/<videoId>`, `#memo/new`, `#memo/<id>`, `#search/<q>`, `#settings`, `#settings/youtube`), the session index, the notes index (`useNotesIndex`), the restore hook and the search state; the sidebar (`SidebarNav`) lists open tabs, saved sessions, the memos (title, last change, a Conflict copy badge; New memo on the heading), the videos with YouTube notes (title, note count, last change) and - folded away, marked "recovered" after a restart - the snapshots. The main pane is one of: `OpenTabsPage` (live `OpenWindowsPane`, one Save button), `SessionPage` (rename, open, open one window, remove a tab/window, export, delete), `SnapshotPage` (open, **Keep** = move into the saved list, delete), `NotesPage` (one video's notes: each time a link to the video at that second through `openVideoAt()`, edit / delete with Undo, Export Markdown through `notesToMarkdown()` in `src/lib/notes-export.ts`, Delete all notes behind `DeleteVideoNotesDialog`), `MemoPage` (one memo, `src/pages/memo.tsx`: its uncontrolled `MemoEditor` saves `POLICY.memo.autosaveMs` after typing pauses, on blur, on Ctrl or Command+Enter, when the page is hidden and on unmount, one save after another through `MemoEditorSession` in `src/lib/memo-editor-state.ts`, each passing the text it last saw saved as its precondition; on `pagehide` it writes a `memoDraft:*` synchronously; Export Markdown; Delete with Undo in a toast), or `SearchResults`. Settings is not a pane: `#settings` draws `SettingsPage` as a dialog over whichever of those was showing (the language menu on its title row, left of the ×; sort settings as dropdowns, the Custom-only ones indented under Sort by and shown only for Custom, the rest under "Advanced"; the YouTube access (allow / remove, for "Pause all YouTube videos"); session settings one per line; backup + `StorageMeter`; and the keyboard shortcuts Chrome reports). Every control writes as it changes - no Save button anywhere. It **runs restores in the page** (never in the service worker, so the worker's idle/lifetime limits do not apply) and talks to `chrome.*` directly - there is no message passing to the worker. `openDashboard()` (`src/lib/open-app-page.ts`) is a singleton: it focuses an existing app tab or creates one. `followSystemTheme()` (`src/lib/theme.ts`) runs once at startup; there is no theme control.
3. **The notes side panel** (`src/notes-panel.html`, `src/pages/notes-panel.tsx`, entry `src/pages/notes-panel-entry.tsx`) - the manifest's `side_panel.default_path`, a second small React page. It follows the active tab of its own window (`useActiveVideo`: page-side `chrome.tabs.onActivated/onUpdated/onAttached/onDetached` listeners, never in the worker), shows that YouTube video's notes, and talks to the page through `chrome.scripting.executeScript` of `controlPlayerInPage` (`src/lib/youtube-player.ts`). It is opened only by `openNotesPanel()` (`src/lib/open-notes-panel.ts`, `chrome.sidePanel.open` from a gesture): the `open-notes` menu item and command in the worker, and the YouTube notes button on the Open tabs view; the icon click never opens it. Its **Screenshot** button runs `captureFrame()` (`captureFrameInPage`: the player's frame drawn into a canvas, scaled to at most 1280 px wide, WebP at 0.8; no video, no picture yet or a tainted canvas comes back as a reason and is shown as an error toast) and stores it with a new note at that time, text optional; each note with a picture shows a thumbnail (`NoteThumbnail`, read by `useNoteImage`) that opens large in `NoteImageDialog`.
4. **Shared code** (`src/components/`, `src/hooks/`, `src/lib/`) - the components, hooks and logic the pages and the worker are built from (`WindowTree`, `ExportMenu`, `ImportDialog`, `ProgressToast`, `useSessionIndex`, `useSessionBody`, `useRestore`, `useOpenWindows` (which registers `chrome.tabs/windows/tabGroups.on*` listeners _in the page_), `useSearchCorpus`, and every module in `src/lib/`). None of it owns a page or registers a worker listener.

There is **no popup**, **no content script** (nothing under `content_scripts`, no `host_permissions`), **no message-passing protocol** and no server other than the optional sync server (`server/`, reached only after the person signs in to cloud sync). The extension icon click directly triggers sorting and nothing else. The only things that ever run inside a web page are `pauseVideosInPage` from `src/lib/pause-youtube.ts`, injected with `chrome.scripting.executeScript` into YouTube tabs when the person chooses "Pause all YouTube videos", and `controlPlayerInPage` from `src/lib/youtube-player.ts` (read the time, length, paused state and title; seek; pause; play) and `captureFrameInPage` from the same file (the Screenshot button: the frame on screen as a WebP data URL), injected by the notes side panel into the YouTube tab it shows; all only once the person granted the optional `https://*.youtube.com/*` host permission (in Settings, or the same switch in the notes panel).

### Data Flow

Sorting (unchanged):

```
User clicks extension icon
-> chrome.action.onClicked listener (src/service-worker.ts)
-> sortTabGroups() (src/lib/sort-tabs.ts)
-> Load settings from chrome.storage.sync
-> Query pinned tabs, tab groups, ungrouped tabs
-> Sort each set independently
-> Move tabs via chrome.tabs.move()
-> Handle duplicates (close or group)
```

Gathering every window into the focused one (`assemble-tabs` - right-click "Assemble!" or the command):

```
Right-click icon → "Assemble!" / keyboard shortcut the user bound at chrome://extensions/shortcuts
-> handleMenuOrCommand('assemble-tabs') (src/service-worker.ts) -> assembleTabs() (src/lib/assemble-tabs.ts)
-> ignored while a run is in progress; nothing to do with a single normal window
-> chrome.windows.getLastFocused({ populate: true, windowTypes: ['normal'] })  // target + its active tab id
-> pickSourceWindows() (pure: other normal windows with the same incognito mode)
-> per source window, planWindowMoves() (pure), replayed in order:
   park the source's active tab on an ungrouped anchor (chrome.tabs.update active, in the source)
 - or, in a window of groups only, chrome.tabs.ungroup the active tab (re-collapsing its group)
   ungrouped runs: chrome.tabs.move(ids); groups: chrome.tabGroups.move(groupId)  // appended
   pinned tabs: chrome.tabs.move(ids) then chrome.tabs.update(id, { pinned: true }) in order
   the anchor last: chrome.tabs.move to its place, or back into its group (chrome.tabs.group)
   (a failing window is recorded and skipped; the rest continue; emptied windows close themselves)
-> restoreTargetView(): race safety net only - normally nothing to put back
-> chrome.windows.update(target, { focused: true }) -> ✓ badge, or ! when any window failed
```

Pausing every YouTube video (`pause-youtube` - right-click "Pause all YouTube videos" or the command):

```
handleMenuOrCommand('pause-youtube') (src/service-worker.ts)
-> hasYoutubeAccess() (chrome.permissions.contains, src/lib/pause-youtube.ts)
   no  -> openDashboard('#settings/youtube'): Settings scrolled to its YouTube row, the switch
          focused and a hint saying why it opened (youtubeAccessHintKey()); turning the switch on calls
          requestYoutubeAccess() from the click (chrome.permissions.request needs a user gesture,
          so the worker never asks itself), and the notice after a grant says to run it again;
          nothing is injected
   yes -> pauseYoutubeTabs(): chrome.tabs.query({ url: YOUTUBE_ORIGINS }) -> pausableTabIds() (pure:
          youtube.com over https, not discarded/unloaded; a frozen tab is kept) -> per tab, in
          parallel, chrome.scripting.executeScript({ func: pauseVideosInPage }) (pauses every
          playing <video>/<audio>, returns the count; a failing tab is recorded, the rest
          continue; a tab silent for PAUSE_ANSWER_TIMEOUT_MS, e.g. frozen, counts as unanswered)
-> no badge when no YouTube tab is open, ! when every tab failed, ✓ otherwise (also when nothing
   was playing). Never a toggle: running it again resumes nothing.
```

Saving a session:

```
Right-click icon menu item / keyboard command / the app page's Save button
-> handleMenuOrCommand(id) (src/service-worker.ts) or src/pages/app.tsx
-> captureSession('window' | 'all' | { windowId }) (src/lib/session-capture.ts)
-> chrome.windows.getAll({ populate: true, windowTypes: ['normal'] })
-> chrome.tabGroups.query({})
-> captureWindows(windows, groups, options) (pure: drops incognito, own pages, empty windows;
   unwraps suspended tabs; groups by first appearance)
-> sessionRepo.put(session) (src/lib/session-repo.ts, under the Web Lock)
-> chrome.storage.local.set({ 'session:<id>': body })  // body first
-> chrome.storage.local.set({ sessionIndex })          // then index (newest first)
-> showSavedBadge() (worker only; cleared after 2 s and at the start of every handler)
```

Restoring a session (the app page only):

```
Open (session / snapshot) -> useRestore()
-> sessionRepo.get(id) + sessionRepo.getSettings()
-> planRestore(session, { target, lazy, sanitize }) (pure: sanitizeRestoreUrl, chunks of 25)
-> executeRestore(plan, { onProgress, signal, screen })
-> windows.create placeholder -> tabs.create per chunk (retry once on "cannot be edited")
-> tabs.discard non-active/non-pinned when lazy -> tabs.group + tabGroups.update after all tabs
-> collapse groups -> activate -> remove placeholder -> apply minimized/maximized/fullscreen
-> ProgressToast with restored / skipped / errors
```

History snapshot (service worker; the alarm, or the icon click while snapshots are on):

```
alarms.onAlarm('history-snapshot' | 'history-first') / second action.onClicked listener
-> takeHistorySnapshot({ origin }) (src/lib/history-snapshots.ts)
-> sessionRepo.getSettings(): 'disabled' when historyEnabled is false (no window query at all)
-> captureSession('all') -> contentHash(windows) vs historyMeta.lastHash -> 'skipped-unchanged'
-> sessionRepo.put({ kind: 'history', name: defaultHistoryName(...) })  // sessionSnapshotDefaultName, in the UI language
-> sessionRepo.pruneHistory(historyMaxSnapshots)   // oldest unprotected history first; never 'saved'
-> sessionRepo.setHistoryMeta({ lastHash, lastSnapshotAt })
```

Search, export and import run entirely in the app page: `useSearchCorpus` builds `SearchEntry[]` per session body (pre-warmed on idle, invalidated per key by `storage.onChanged`) plus the open-windows snapshot, `useMemoSearchEntries` one per memo (`entryFromMemo`: the title is the first line, the whole text the `context`, always searched, read again when its `updatedAt` changes, `memosToLoad()`), `useNotesSearchEntries` adds one entry per YouTube note (`entriesFromNotes`: the note's text as the title, the video's title as `context`; every video read on idle and read again only when its `updatedAt` in `notesIndex` changes, `notesToLoad()`), and they feed `search()` from `src/lib/search-engine.ts`; `ExportMenu` calls the pure serializers in `src/lib/session-export.ts` and hands the text to `src/lib/download-and-copy.ts` (Blob URL + `<a download>` - no `downloads` permission) or to the clipboard; `ImportDialog` runs `importSessions()` from `src/lib/session-import.ts` (type guards in `import-guards.ts`), shows a preview, then `sessionRepo.put()` per session.

Sort settings are persisted in `chrome.storage.sync` and loaded fresh on every sort invocation. Session data and `sessionSettings` live in `chrome.storage.local` and are read through `sessionRepo` only. The dashboard reloads its list when `chrome.storage.onChanged` reports a change to `sessionIndex`, and `useSessionSettings` re-reads on a `sessionSettings` change.

**Layout rules (set by the owner).** `src/pages/` holds screens (the page entry, `app.tsx` and its views); `src/components/` holds every hand-made component, flat; `src/components/ui/` holds stock shadcn/ui components only, as the CLI writes them, and never a custom component (a component built on top of one goes in `src/components/`); `src/hooks/` holds React hooks, flat; `src/lib/` holds all logic, one level only with no subfolders; `src/styles/index.css` is the one stylesheet; `src/service-worker.ts` is the worker. Tests live in `src/tests/`, flat, never next to their source (every package: see Tests below). A new file goes in the folder its kind names, not next to whatever uses it. So a file in `src/pages/` is one screen component and nothing else: its own `Props` interface (not exported) and private constants. A non-React function it needs, even one only it calls, goes to `src/lib/` (tested in `src/tests/` when it decides something); a hook to `src/hooks/use-*.ts`; a sub-component to `src/components/`. Export only what another file imports - tests count, so a pure half exported for its unit test stays exported.

**Tests are always inside `src/` (set by the owner).** In every package, a test and its helpers go in that package's `src/tests/`: `src/tests/` for the extension, `server/src/tests/` for the sync server, `site/src/tests/` if the website gets tests. Never create a `tests/`, `test/` or `__tests__/` folder beside a `src/` or at a package root, and point a new package's test runner at `src/tests/`. A script run by hand is a script, not a test: `scripts/` (`scripts/e2e/` included) stays where it is.

**File names are kebab-case everywhere** (`sidebar-nav.tsx`, `use-open-windows.ts`, `session-repo.ts`, `close-tabs-dialog.test.ts`), the convention the stock shadcn files in `src/components/ui/` already use. What is inside follows TypeScript and React: components are PascalCase (`SidebarNav`), hooks and functions camelCase (`useOpenWindows`, `sortTabGroups`), constants UPPER_SNAKE_CASE. Name a lib file for what it holds (`session-repo.ts`, not `storage.ts`): with one flat folder, a generic name says nothing.

**The owner's exception to kebab-case:** the sync server's two entry points are named exactly `vercel.adaptor.ts` (`server/api/`) and `railway.adaptor.ts` (`server/src/`). The dot and the spelling "adaptor" are intended: never rename them to kebab-case or "adapter".

### `src/lib/sort-tabs.ts`: Sort orchestration & Chrome APIs

Handles settings loading, Chrome API calls (`tabs.move`, `tabs.group`, `tabGroups.update`), and duplicate tab handling for the icon click; the listener that calls `sortTabGroups()` is in `src/service-worker.ts`. Imports pure sorting logic from `sort-order.ts`.

| Function                | Purpose                                                                                                                                                                            |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sortTabGroups()`       | Main orchestrator. Loads settings, queries tabs, delegates to sort functions, handles duplicates.                                                                                  |
| `sortTabs()`            | Sorts a set of tabs, then runs the `planMoves()` batches from `move-plan.ts` - no call at all when the order is already right. Dispatches to `sortByTitleOrUrl` or `sortByCustom`. |
| `handleDuplicateTabs()` | Finds duplicate URLs and either closes extras or groups them.                                                                                                                      |
| `closeDuplicateTabs()`  | Keeps active/first tab, closes the rest.                                                                                                                                           |
| `groupDuplicateTabs()`  | Groups duplicate tabs into a Chrome tab group.                                                                                                                                     |

### `src/lib/assemble-tabs.ts` - Gather all windows into one

Moves every tab of the other normal windows into the last-focused normal window. **Only `chrome.tabs.move` / `chrome.tabGroups.move`** - never reopen by URL and close, never duplicate - so tab ids, history and page state survive and a failed call leaves a tab in its window. Pure halves: `pickSourceWindows(windows, target)` (other `type: 'normal'` windows with the target's `incognito`) and `planWindowMoves(tabs)` (see below). `assembleTabs()` runs them per source window with a per-window try/catch and one retry on "Tabs cannot be edited right now" (`withRetryOnce` from `src/lib/session-restore.ts`), guarded by a module-level in-progress flag. Chrome behaviours it depends on, verified in a real browser (see Real-Chrome QA): a cross-window `tabs.move` drops `pinned` (re-pin in order and each lands at the end of the target's pinned area); `tabGroups.move` keeps the group id, title, colour and collapsed state - **but** a group holding its source window's active tab makes that tab the target's active tab and expands the group (`tabs.move` never activates anything). The owner's rule is that the target's active tab never changes, not even for a moment, so this is prevented, not repaired: before any group moves, the source window's active tab is parked on an ungrouped anchor that moves last - the active tab itself when ungrouped, else a pinned tab (the pinned block then moves last), else the last ungrouped tab (moved last to just before the tab that followed it). Activating an ungrouped tab expands nothing; activating a tab inside a collapsed group would expand it. A window of groups only takes its active tab out of its group (`tabs.ungroup`; from the middle of a collapsed group that expands the group, which is collapsed again at once), moves the groups, then puts the tab back into the same group at the same offset (`rejoin`). A single-tab group vanishes when emptied, so it is rebuilt with the same title, colour and collapsed state (`regroup` - the one case where the group id changes). `restoreTargetView()` is only a safety net for races (e.g. the user activating a tab in a window that is still being emptied).

### `src/lib/sort-order.ts` - Pure Sorting Logic

Contains all pure sorting and grouping functions, extracted for testability. No Chrome API side effects. Both sorts build one `TabSortKey` per tab (pinned, suspended, group position, text) through `sortedByKey()` instead of parsing urls inside the comparator, and every text comparison goes through one module-level `Intl.Collator` - the same result as argument-less `localeCompare`. They still reorder the array they are given.

### `src/lib/move-plan.ts` - Which tabs to move

Pure. `planMoves(current, desired)` returns the `chrome.tabs.move` calls (`MoveBatch[]`, indices relative to the block's first tab) that turn one order of a contiguous block into another, and `[]` when nothing is out of place. It prices two candidates as _tabs displaced + calls_ and takes the cheaper: `fewestDisplaced` keeps the longest already-ordered run (`longestIncreasingRun`, patience sorting) and moves only the rest, joining moves onto consecutive indices into one call; `wholeBlock` is the single call the sorter always made, which wins when the order is thoroughly shuffled. The weights are measured, not guessed (Chrome for Testing 153, 300 tabs): a tab that really changes place costs about 1.2 ms, a tab asked to move to where it already is costs almost nothing, and a call that moves something adds about one more tab's worth. `applyMoves()` models Chrome's block move for the tests; `isContiguous()` is the guard `sortTabs()` uses before trusting relative indices (otherwise it falls back to the whole-block call). A plan is only right for the order it was made from, so the sorting `action.onClicked` listener in `src/service-worker.ts` chains runs on a module-level promise (`sortQueue`): a double click sorts twice in sequence, never side by side (`src/tests/service-worker-sort.test.ts`).

| Function               | Purpose                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| `sortByTitleOrUrl()`   | Sorts tabs alphabetically by title or URL. Handles suspended tab grouping and pinned tab exclusion.     |
| `sortByCustom()`       | Groups tabs by hostname/domain, preserving first-seen order. Supports LTR/RTL grouping direction.       |
| `findDuplicateTabs()`  | Returns a `Map<url, Tab[]>` of URLs with more than one tab.                                             |
| `extractGroupingKey()` | Parses hostname into grouping key. In `domain` mode, handles two-part TLDs (e.g., `co.uk`).             |
| `isSuspended()`        | Whether a tab shows a tab suspender's page (`isSuspendedUrl()` from `suspended-url.ts`, any suspender). |
| `tabToUrl()`           | The url a tab sorts by: a suspended tab's real url, unwrapped verbatim by `unwrapSuspendedUrl()`.       |
| `urlSortKey()`         | The text a url sorts by (hostname without `www.`, then path, query, hash), computed once per tab.       |
| `sortedByKey()`        | Stable decorate-sort-undecorate: derives each item's key once, compares keys only, returns a new array. |
| `hashStringToColor()`  | Deterministically maps a string to a Chrome tab group color.                                            |
| `updateTabGroupMap()`  | Tracks first-seen ordering of tab groups by hostname/domain grouping key.                               |

### Enforced by oxfmt (`.oxfmtrc.json`) and oxlint (`.oxlintrc.json`)

- **Line width**: 100 characters
- **Line endings**: LF
- **Quotes**: Single quotes for JS/TS, double quotes for JSX
- **Semicolons**: Always
- **Trailing commas**: Always
- **Imports**: sorted by oxfmt (`sortImports`)
- **No em or en dashes** (set by the owner): never write U+2014 or U+2013 anywhere in the repository, in code, comments, docs, UI text, commit messages or PR text; use a plain hyphen-minus (`-`). `scripts/check-dashes.ts` (`pnpm check:dashes`, part of `pnpm lint` and the pre-commit hook) fails on any tracked file that has one
- **Block statements**: Required (oxlint `curly: all`)
- **Lint rules**: oxlint's correctness category as errors, plus `react/no-array-index-key`, `react/no-danger`, `jsx-a11y/prefer-tag-over-role` and `jsx-a11y/no-noninteractive-element-to-interactive-role`. A deliberate exception is an `oxlint-disable-next-line <rule> -- <reason>` comment on the line above, always with the reason

### TypeScript

- Strict mode enabled
- Path alias: `@/*` maps to `./src/*`
- No `any` types - use proper type narrowing (see the type guards in `src/lib/import-guards.ts` and `src/lib/sort-settings.ts`)
- Chrome API types from `@types/chrome`

### Policy numbers (set by the owner)

- **Every policy number goes into `POLICY` in `src/constants.ts` and nowhere else**: limits, sizes, lifetimes, periods, bounds and defaults the owner would tune. Read it where it is used (`POLICY.account.screenshots`): no local constant, alias or copy, in the extension or in `server/`. Numbers quoted in this file and the READMEs only describe it; the object wins, and a change to it updates them, plus the website, the store text and `PRIVACY_POLICY.md` where they quote it.
- Not policy, so they stay where they are used: UI timings, layout numbers and format invariants (IV, key and token byte sizes, the id pattern, schema versions).
- The server imports the same file by relative path (`../../src/constants.js` from `server/src/`), so `src/constants.ts` has no imports.
- One edit changes both sides, but they ship apart and released extensions keep their old numbers. **Widen** what the server accepts (a higher maximum, a lower minimum) by deploying the server before the extension that uses it. **Narrow** it (a lower maximum, a higher minimum) by releasing the extension first and holding the server deploy until older versions no longer send what it would refuse. `POLICY.kdf` is part of envelope version 2: the parameters never travel with an envelope, so changing them needs a new envelope version that every extension in use can read first.
- A function serialized into a page (`chrome.scripting`) cannot read `POLICY`: pass the value in `args`, as `captureFrame()` does.
- `src/tests/policy.test.ts` pins every value and checks that the client and the server's validation agree at the boundaries. Tests may spell numbers out; a SQL migration is never edited for one (pass it as a parameter).
- `account.storageBytes` is a hard bound on the server (every row counts at least a tombstone, deletions always pass), and `normalizeSettings()` clamps a stored or synced `historyMaxSnapshots` to `snapshots.keep` (#270).

## Chrome Extension Specifics

### Manifest V3

The manifest is generated at build time from `vite.config.ts`. Key points:

- **Service Worker**: `src/service-worker.ts` (module type), the only module the manifest names for the worker
- **One page**: `app.html` (`build.rollupOptions.input`), opened only through `openDashboard()`, so there is only ever one app tab. It is the only HTML page; Chrome's "Options" opens `app.html#settings` directly.
- **Options Page**: `options_page: 'app.html#settings'` (not `options_ui` - full-page, not embedded). A fragment in `options_page` is accepted; verified in Chrome for Testing 151.
- **No popup**: Extension icon click triggers sorting directly. `action.default_title` is the tooltip that tells a first-time user about the right-click menu.
- **No content scripts**: All operations use Chrome APIs only
- **Side panel**: `side_panel.default_path: 'notes-panel.html'` (YouTube notes). `openPanelOnActionClick` stays at its default, false: the icon click sorts and never opens it.
- **Commands**: `_execute_action` (sort - the icon click), `save-session`, `open-dashboard`, `assemble-tabs`, `pause-youtube`, `open-notes` - sorting suggests `Alt+Shift+S`, assembling `Alt+Shift+A` and pausing YouTube `Alt+Shift+P`; the other three are unbound by default (users assign keys at `chrome://extensions/shortcuts`).
- **Minimum Chrome**: `minimum_chrome_version: '123'`. Raise it only for an API used without a runtime guard, and say why in the `vite.config.ts` comment.

### Storage Schema

**`chrome.storage.sync`** - `SortSettings` (defaults `DEFAULT_SORT_SETTINGS` in `src/lib/sort-settings.ts`), and `uiLanguage` (`'auto' | SupportedLocale`, default `'auto'`, anything else reads as `'auto'`; `src/lib/ui-language.ts`, never part of `SortSettings` / `SORT_SETTING_KEYS`). A `tabSuspenderExtensionId` key an older version stored there is no longer read or written (suspended tabs are recognised by shape, see `src/lib/suspended-url.ts`); it is left in place, never deleted. Sessions code never touches `chrome.storage.sync`: not the sessions modules of `src/lib/`, nor `src/hooks/`, `src/components/` or `src/pages/` (`sort-tabs.ts`, the Settings view's sort settings and `ui-language.ts` are the only sync access). Every change is one `set` of body (or `null`), index and sync bookkeeping, then the cleanup `remove` of the `null` keys. `sessionRepo.reconcile()` (app-page mount, `onInstalled`, `onStartup`) re-indexes orphan `session:*` bodies via `chrome.storage.local.getKeys()` (guarded fallback to `get(null)`), drops index entries without a body, and re-derives an entry that no longer matches its body. It is the **repair** path, so it is the one reader that tolerates an unreadable index: it treats it as empty and rebuilds it from the bodies. Every mutation still rejects on a future-schema index - this build must not overwrite a store a newer one wrote. A future-schema _body_ is kept and flagged instead of dropped (`SessionSummary.unreadable`), so a downgrade shows an inert "saved by a newer version" row the user can delete rather than an empty list. `sessionRepo.removeAll()` ("Delete all session data" in the dashboard's `StorageMeter`) removes every `session:*` body, `sessionIndex` and `historyMeta` under the lock; `sessionSettings` survives. `chrome.storage.local.getBytesInUse()` feeds the meter. Under it the meter shows where that data is on disk: Chrome keeps `chrome.storage.local` as a LevelDB in the profile folder, `<profile>/Local Extension Settings/<chrome.runtime.id>/`; `src/lib/storage-location.ts` builds the path for this OS (`storageOsOf()` over `navigator.userAgentData.platform` or `navigator.platform`, `storageFolderPath()` for the `Default` profile; nothing on ChromeOS), with Copy path and Find profile folder (`openChromeVersion()`: chrome://version shows the exact Profile Path, since an extension can read neither the profile path nor open a file manager).

`shortcutPrompted` (`string[]` in `chrome.storage.local`, `src/lib/keyboard-shortcuts.ts`) holds the command ids the shortcuts toast has already named, so it is never shown twice for one; not session data, never through `sessionRepo`.

**YouTube notes** follow the sessions pattern with a lock of their own (`tabinet:notes`, so a notes write never waits on a session write): every write goes through `notesRepo`, image, body, index and sync bookkeeping in one `set` (`runDocTransaction()` in `src/lib/doc-store-tx.ts`); `notesRepo.reconcile()` (`onInstalled`, `onStartup`) re-indexes orphan bodies, drops index entries without one, rebuilds an unreadable index and removes images no note references (none while a body cannot be read, nor one cloud sync holds live and may still bring the note for). A body or index from a newer schema throws `UnknownSchemaVersionError` and is never written over. Deleting a video's last note deletes the video; "Delete all session data" leaves notes alone. Cloud sync: every write tracks its entry through `trackLocalDocChange()` and the engine applies what the server sent through `youtubeNoteStore`, both with the sessions lock taken **inside** the notes lock (the bookkeeping is written under the sessions lock). The order is always the store's lock, then sessions: nothing that holds the sessions lock may wait for the notes or memos lock, or they could deadlock.

**Memos** follow the same pattern with the lock `tabinet:memos`: every write goes through `memoRepo` (`save`, `remove`, `restore`, `adoptDrafts`, `reconcile`), body, index and bookkeeping in one `set`, and writes happen with sync unconfigured too, with no bookkeeping read. `save({ id, text, expected })` decides by text, never by stamp: unchanged when the memo holds the text, written when it holds a text in `expected`, written into sync's conflict copy of this editor's text when there is one (`redirected`), otherwise a copy by the copy-id rule (`copied`); the editor follows the memo returned. A memo body this build cannot read is never written over, and the page shows it as unreadable. "Delete all session data" leaves memos alone. The panel's "Pause the video while I write" box is a `localStorage` preference (`NOTES_PAUSE_KEY` in `src/lib/ui-state.ts`), not user data.

**`sessionStorage`** (the app tab only) - `src/lib/ui-state.ts` keeps one per-tab UI flag there (`tab-organizer:history-open`). Not user data, never `chrome.storage`, never through `sessionRepo`; both accessors are guarded because `sessionStorage` is absent under vitest and throws when the browser blocks site data.

### Sessions rules (do not break)

- **Single write path.** Every write to session keys goes through `sessionRepo` in `src/lib/session-repo.ts`, which serializes with `withLock()` (`navigator.locks.request('tab-organizer:sessions', …)`, shared by the service worker and both extension pages; promise-chain fallback when Web Locks are unavailable). Never call `chrome.storage.local.set/remove` for session keys anywhere else.
- **Never add tab listeners to the service worker.** No `chrome.tabs.on*`, `chrome.windows.on*`, `chrome.tabGroups.on*` in `src/service-worker.ts`, or in any module it imports at load time - ever. History uses `chrome.alarms` only; the dashboard's live open-windows pane registers its listeners inside the page (`useOpenWindows`), where they die with the tab. Every worker listener is registered synchronously at module top level of `src/service-worker.ts` - never inside an async callback or after an `await`.
- **Sessions code never touches `chrome.storage.sync`** - no read, no write. The one exception is cloud sync's settings path in `src/lib/cloud-sync.ts` (`readLocalSettings()` and the apply step of `applySettingsRecord()`), which reads and writes the sort settings and `uiLanguage` there because that is where they live; nothing else in sessions code may. Suspended tabs are recognised by the shape of their url (`src/lib/suspended-url.ts`), not by a stored id. Session data and session settings live in `chrome.storage.local` only.
- **The icon click stays `sortTabGroups()` only.** No `default_popup`, no dialogs, no `openDashboard()` on `action.onClicked`. `sort-order.ts` and the duplicate handlers are not edited by session work.
- **Restore runs in the app page**, never in the worker. Own extension pages are excluded from every capture.
- **No Chrome runtime ids in stored data** - groups are referenced by `groupIndex`; pinned tabs never carry `groupIndex`; at most one `active` tab per window.
- **A chrome namespace touched at module-evaluation time needs its permission in the same commit.** Anything `src/service-worker.ts` (or any module it imports) reads or calls while the module body runs, such as `chrome.alarms.onAlarm.addListener(…)`, `chrome.something.CONSTANT` or a top-level `chrome.x.y()`, runs while the one worker module evaluates, and the imported modules' bodies run before the worker's own. A missing permission makes that line throw, the whole service-worker module fails to evaluate, and every listener after it is never registered: the sorting `chrome.action.onClicked` sits near the end of the file, so **tab sorting dies too** - a permission typo takes out the unrelated core feature, not just sessions. So add the permission to `vite.config.ts` in the very same commit as the code that touches the namespace (never "wire it up now, add the permission later"). `alarms` is the live example: `chrome.alarms.onAlarm.addListener` in `src/service-worker.ts` and `'alarms'` in `permissions` landed together and must stay together.

## Cloud sync (on, opt-in per person)

Protocol v2 (v10; issues #264 server, #265 key wrapping, #266 doc records, #267 memos, #259 streaming, #261 the 50 MiB cap, #268 cutover). It ships switched on and stays opt-in for each person: nothing is sent until they press Sign in with Google in Settings > Account. Protocol v1 (`/v1/*`, a passphrase-derived key, one `notes` record per video) is closed: the server answers every `/v1` request 410 `upgrade_required`, and no v1 row, key or bearer is accepted or migrated. `CLOUD_SYNC = { apiBase, googleClientId }` in `src/constants.ts` names the deployed server (`https://tabinet-server.vercel.app`) and the Google OAuth client (type "Chrome extension", bound to the store item id); `cloudSyncConfigured()` is true only when both are set, so `cloudSyncPermissions()` is `['identity']` and `cloudSyncOauth2()` gives the `oauth2` key (`openid`, `email`, `GOOGLE_OAUTH_SCOPES`), `vite.config.ts` spreads both into the manifest, and `SettingsPage` shows the Account section. Clearing `apiBase` makes a build dormant: no `identity`, no `oauth2`, no Account section, and every entry point returns at once with no storage read, alarm or fetch. The manifest carries no `key`, so an unpacked build has another extension id and `getAuthToken` refuses the client there: `canSignInHere()` (`src/lib/cloud-config.ts`, the id against `STORE_EXTENSION_ID`) disables Sign in outside the store build. Running code reads the config through `cloudSyncConfig()` / `isCloudSyncEnabled()`; tests point it at a fake with `overrideCloudSyncConfig(getter)`. `identity` is justified in `PERMISSION_JUSTIFICATIONS` (`scripts/store-listing.ts`), and `PRIVACY_POLICY.md` ("Cloud sync") with its translations, the store text, the website and README describe what sync sends: change them together with any change to what is synced or where the server runs.

**Invariants (do not break).** The server never receives a passphrase, data key (DEK), wrapping key or plaintext record. Local user data from 8.3 to 9.x is never rewritten into another format by the upgrade. A pull without its end line is a failed run and never continues to a push. A deletion is never refused for a cap. Only sign-out, a confirmed deletion and a confirmed replacement remove a DEK (a 401, expiry, 403, 409, 410 or 5xx never does). Nothing is uploaded to another account before the person says yes (the default is no). Network calls never run inside a repository lock. Every local change and every applied remote batch of one repository is **one** `chrome.storage.local.set` (bodies, deleted keys as `null`, index, bookkeeping); the later `remove` of the `null` keys is cleanup only, and every reader treats a `null` value as absent. An item this build cannot read (an unreadable local body, an unknown doc type, a newer version) is never overwritten or pushed over: it is held with a replay floor.

**Keys** (`src/lib/cloud-crypto.ts`, WebCrypto only; vectors in `src/tests/key-vectors.json`). The first device makes `dek`, 32 random bytes that never change, the AES-GCM key of every record. From it, by HKDF-SHA-256: `keyId` (16 bytes, b64u, names the key everywhere), `writeProof` (sent only to `PUT /v2/keys`; the server stores its SHA-256, `writeVerifier`, so only a DEK holder can replace the envelope) and `docIdKey` (memory only, for doc record ids). The passphrase (NFC, never trimmed, at least `POLICY.passphrase.minLength` code points for a new one, no minimum to unlock) derives `wrapKey` by PBKDF2-SHA-256 with `POLICY.kdf.iterations` rounds and a 16-byte salt; `KeyEnvelope` `{ v: 2, generation, keyId, salt, iv, wrapped }` is the DEK wrapped under it, with `["tabinet-wrap-v2", generation, keyId, salt]` as AAD. The server seals the envelope again under its own key encryption key, bound to the Google `sub` verified in that request, and opens it only for a request whose Google token verifies as the same account. Exports: `createKey()`, `rewrapKey()`, `unwrapKey()` (null for a wrong passphrase or a keyId that does not match), `docRecordId(dek, type, id)` (HMAC-SHA-256 of `type || 0x00 || id`, 43 characters), `memoCopyId(originalId, text, n)`, `encryptRecord()` / `decryptRecord()` (the record's `{ kind, id, updatedAt, deleted }` bound as AAD, `tabinet-record-v1|<kind>|<id>|<updatedAt>|<0 or 1>`, so a moved, replayed or flipped record does not decrypt; `CloudDecryptError`). Changing the passphrase is a new envelope over the same DEK at generation + 1; it does not revoke a DEK someone already has (only Delete cloud data does).

**Account** (`src/lib/cloud-auth.ts`, page only; `src/lib/cloud-storage.ts` holds the key names, guards and compare-and-write helpers, with no imports from repositories). Every key operation: synchronous form validation, then `getAuthToken({ interactive: true })` from that click, then the slow work and the request, then `removeCachedAuthToken` in `finally`; the Google token lives in that function only, and every store after an await is compare-and-write against the bearer it started with. A closed consent window is `{ outcome: 'cancelled' }` (`isSignInCancelled()`), never a throw. `accountState()` (pure) gives `unconfigured | loading | signedOut | expired | confirmAccount | keyMismatch | ready | unknown | needsCreate | needsUnlock` from the stored account, key and the server's last `WireKey`; only `ready` syncs (live account, `uploadConfirmed`, a key of that account). Actions: `signIn()` (asks `confirmAccount` when `cloudOwnerV2` names another account), `confirmAccount()` / `cancelAccountSwitch()` ("No, keep it here" is the focused default and uploads nothing), `createPassphrase()` (only after 201 are key and owner written; 409 `key_exists` goes to Unlock), `unlockWithPassphrase()` (generation at least me's, same keyId; a wrong passphrase writes nothing), `changePassphrase()` (from any ready device, without the old passphrase: also the reset of a forgotten one; the confirmed generation the PUT returned is stored, which ends a rollback warning), `signOut()` (removes the key too, with a warning dialog), `deleteCloudData()` (after 204 only: the account, the key, `owner` set to `{ accountId: null, email }`, the bookkeeping and every `cloudRaw:*`). `google_account_mismatch` clears Chrome's cached tokens and says to choose the right account, and never advises signing out. Settings > Account (`src/components/account-field.tsx`, `confirm-account-field.tsx`, `change-passphrase-dialog.tsx`, `sign-out-dialog.tsx`, `delete-cloud-data-dialog.tsx`, `cloud-usage-field.tsx`, `sync-status-field.tsx`, `sync-help.tsx`, over `src/hooks/use-cloud-account.ts` and `use-cloud-sync.ts`) shows one row per state; passphrase fields are uncontrolled and validated on submit. **Cloud storage** shows `cloudUsageText(usage, limit)` (`src/lib/cloud-usage.ts`, 1024-based, `12.3 MB / 50 MB`), preferring the last sync's usage over `GET /v2/me`'s.

**Upgrade** (`upgradeCloudStorage()` in `src/lib/cloud-storage.ts`, idempotent: `onInstalled`, the start of `syncNow()` and the account hook, since a page can open before `onInstalled` ran). Under the account lock, when a v1 key (`cloudAccount`, `cloudSyncKey`, `cloudSyncMeta`) exists: its email becomes `cloudOwnerV2 = { accountId: null, email, legacy: true }` (Settings then shows `settingsAccountUpgradeHint`), and the three v1 keys go in the same `set`. Nothing else: sessions, notes and screenshots stay byte for byte. Stamps entering the bookkeeping are validated (`stampOf()`: a safe integer of at least 1, one more than `maxClockAheadMs` ahead becomes now).

**The engine** (`src/lib/cloud-sync.ts`; bookkeeping `cloudSyncMetaV2` in `src/lib/cloud-sync-state.ts`, always under the sessions lock; doc machinery in `src/lib/cloud-docs.ts`). Record kinds: `session` (id = session id, the whole saved `Session`, last writer wins on `updatedAt`), `settings` (id `settings`, `{ sort, sessionSettings, uiLanguage }`, never deleted), `image` (a screenshot's data URL; immutable, the newer stamp wins) and `doc` (an opaque HMAC id; content `{ type, version, data }`). A tombstone is `deleted: true` with `{ deleted: true }` (or the collection's deleted data for a doc) encrypted inside, so the server cannot forge one. Snapshots never sync. `syncNow()` runs under the Web Lock `tabinet:cloud-sync` (page and worker never at once): upgrade, the ready context (else `notReady`), the meta of `(accountId, keyId)` or a fresh one (every `cloudRaw:*` dropped), failures counted at the start, keepalive (`chrome.runtime.getPlatformInfo()` every `POLICY.sync.keepAliveMs`), tracking started for every collection not in `meta.started`, held items retried, pending settings finished, then:

- **Pull** (`streamRecords()` in `src/lib/cloud-api.ts`): `GET /v2/records?since=<cursor>` with `Tabinet-Key-Id`, NDJSON `start (record+ checkpoint)* end`, split incrementally with a fatal streaming UTF-8 decoder, a `readIdleMs` watchdog only while awaiting a read. At each checkpoint the batch is decrypted and checked outside the locks, applied (each store once, sessions then `DOC_STORES` with their screenshots, then settings, then held marks), and only then the cursor is stored. No end line is `errorCloudInterrupted` and a failed run (no push). `complete: false` asks again, up to `maxRequestsPerRun`, then `pullIncomplete`. A `through` below `since` means a rewound database: one reread from 0. A record that fails decryption, its metadata, the HMAC or the doc envelope check is marked `unreadable` and never applied.
- **Restamp**: any pending stamp more than `maxClockAheadMs` ahead becomes `max(now, known + 1)`, so a clock that was wrong stops blocking edits once it is fixed.
- **Push**, in passes: tombstones of sessions and docs first (they make room), then image tombstones whose owning note's deletion was accepted, then live sessions, docs and settings, then live images, and once more for items a falling usage released. Batches of at most `maxRecordsPerPush` and `pushBatchBytes` (in the worker the stored `pushBatchBytes`, halved after a timeout and doubled back when a smaller one answers in time). A doc carries `baseSeq` (compare and swap on the server) and is remembered in `sent` before the POST, so a push whose answer was lost settles without a copy. Results: `applied` drops the pending entry if unchanged; `absent` settles a deletion of a row the server never had; `stale` applies the readable `current` (one that fails AES re-bases the pending version on its `seq` and stamps it above, which is how a junk row is replaced; one that decrypts but this build cannot read, such as a newer session schema, is marked unreadable and never pushed over, the pending change kept as it is); `rejected` `image_limit` / `storage_limit` holds the item (`held`, with the usage reported, released when usage falls or the item is edited; one toast per non-empty set, `useSyncNotices()`), `clock_ahead` keeps it pending with `errorCloudClock`. Results are checked one to one by position, kind and id.
- **Held items** (8.3): a remote record that cannot be applied here (an unreadable local body, a newer version, an unknown doc type) is kept raw under `cloudRaw:<kind>:<recordId>` with `blocked[ref]`, in the same `set`; a later record replaces it only when newer (the replay floor); its push is skipped; it is applied from the raw copy once this build can, and only after that write do its raw copy and mark go (a run cut in between applies it again, which the replay floors make harmless).
- **Triggers** (`src/service-worker.ts`, `src/lib/cloud-sync-scheduler.ts`; no new permission): at once when the account and key become ready (a generation update does not count); `POLICY.sync.debounceMs` after `changedAt` moves (a change of this device's own), at most `maxWaitMs` into a burst; the one-shot `cloud-sync-soon` alarm (`fallbackMs`, the fallback for a worker that died, and the retry, doubling per failure up to the period); the periodic `cloud-sync` alarm every `periodMinutes`; the app page's load; Sync now. Never trigger on the bookkeeping growing: a run's own writes grow it. The first progress of a run resets the backoff to `fallbackMs`.
- **Status** (`src/lib/cloud-sync-status.ts`): `syncing`, `failed`, `sendingSoon`, `tooLarge`, `unreadable`, `partial` (also `pullIncomplete`), `waiting`, `held` (both caps), `upToDate`, `notSynced`; `SteadyText` keeps the row from moving. The ? (`SyncHelp`) text is `syncHelp()`, built from the same constants.

**Collections** (`src/lib/cloud-docs.ts` declares `DocCollection`, `DocStore`, `DocTx`, `resolveDoc()` (pure) and the generic steps; `src/lib/doc-collections.ts` is the one list, `DOC_STORES = [memoStore, youtubeNoteStore]`, in apply order). A store's `transact()` takes its own lock, then the sessions lock, over a working copy of the bookkeeping, and commits everything in one `set` (`runDocTransaction()` in `src/lib/doc-store-tx.ts`; with sync unconfigured it neither takes the sessions lock nor reads the bookkeeping). A store records its own write only through `trackLocalDocChange()`, which returns the stamp (`max(now, previous + 1, known + 1, pending + 1)`) and tracks nothing before the collection's tracking started for this key (`startDocTracking()` then offers every item once). `resolveDoc()`: an echo or replay at or below `known` never applies content; a version matching `sent` settles; otherwise `known` rises and, against a pending local version, `lastWriter` keeps the later stamp (remote wins a tie) while `keepBoth` keeps both texts. An untouched automatic copy always yields. A kept pending version at or below `known` is restamped above it.

- **YouTube notes** (`youtubeNoteStore` in `src/lib/notes-repo.ts`, `lastWriter`): one doc per entry, `{ type: 'youtubeNote', version: 1, data: { id, videoId, title, at, text, imageId?, createdAt } }`, deleted data `{ id, videoId }`, fingerprint `[videoId, title, at, text, imageId]`; the local format (`notes:<videoId>`, schema 1) is unchanged, a change writes only that entry's doc, Delete all is one tombstone per entry, Undo restamps above the tombstone, a non-empty title replaces the video's only from the newest entry. Screenshots follow their notes (the engine owns `image`): a note's deletion records its picture's tombstone with that note as its owner, sent only once the note's own deletion was accepted; a picture a readable note references survives a tombstone and is sent again.
- **Memos** (`memoStore` in `src/lib/memo-repo.ts`, `keepBoth`): `{ type: 'memo', version: 1, data: { id, text, createdAt, conflictOf? } }`, deleted data `{ id }`, fingerprint `[text]`. An edit against another text: the server's keeps the id and this text becomes a copy whose id is `memoCopyId(originalId, text, n)` (the same copy on every device and replay), `conflictOf: originalId`, `autoCopy: true` until it is edited, counted in `conflicts` (the app page says so once, `useConflictNotice()`, then `markConflictsNoticed()`). An edit beats a deletion. Equal texts never copy.

**Tests.** `src/tests/cloud-contract.test.ts` runs the real client (`cloud-api.ts`, `cloud-auth.ts`, `syncNow()`) against the real `createApp()` on PGlite with the migrations, an injected Google verifier and a test key encryption key. `doc-engine.test.ts` runs the engine with test collections (`src/tests/doc-test-stores.ts`) and a seeded property test of `resolveDoc()`; `doc-memo-property.test.ts` runs the real memo and note stores between two and three simulated devices (every row of the memo table, replays, the editor writing into sync's copy, notes added on two devices, edit against delete, Undo after a sent deletion, titles); `src/tests/cloud-fetch.ts` is the fake v2 server (NDJSON, CAS, caps, `absent`, `clock_ahead`, and lies on request). Also `cloud-sync*.test.ts`, `cloud-api`, `cloud-auth`, `cloud-crypto`, `cloud-usage`, `upgrade.test.ts` (with `upgrade-fixtures.ts`), `policy-client.test.ts`, `service-worker-sync.test.ts`. ## Internationalization

The extension speaks English (`en`, the manifest's `default_locale`), Spanish (`es`), Korean (`ko`) and Japanese (`ja`), always listed in that order (set by the owner: the order of `SUPPORTED_LOCALES`; never sort it, and keep hand-written lists in it), through Chrome's own `chrome.i18n`. By default ("Automatic") Chrome picks the browser's UI language (`chrome://settings/languages`, "Display Google Chrome in this language"; on macOS the system language order) and uses the closest `_locales` folder (`es-419` reads `es`), falling back to English for a language that is not shipped and, key by key, for a message a language lacks. That is why English must hold every key.

**The language menu in Settings.** A person can override Chrome's choice from the menu on the Settings dialog's title row (Automatic, English, Español, 한국어, 日本語 - endonyms, from `LOCALE_ENDONYMS` in `src/constants.ts`). The choice is `uiLanguage` in `chrome.storage.sync` (`src/lib/ui-language.ts`). `chrome.i18n` cannot be switched at run time, so the override lives in `src/lib/i18n.ts`: `applyUiLanguage(choice, read?)` loads the chosen `_locales/<code>/messages.json` and English (`fetch(chrome.runtime.getURL(...))`, which works in the page and the worker; `read` is injectable, and tests pass `readLocaleFile` from `src/tests/chrome-fake.ts`), and `t()` / `tp()` then fill them in through `formatMessage()` exactly as `chrome.i18n.getMessage` does (named placeholders first, `$1`..`$9`, `$$`, a missing substitution empty, per-key English fallback); `'auto'` goes back to `chrome.i18n`. `uiLocale()` follows on its own, because it reads `localeCode` through `t()`. The app page awaits `applyStoredUiLanguage()` in `src/pages/index.tsx` before the first render; choosing a language writes the setting and reloads the page, so every string, module-level formatter and `Intl` object is rebuilt in it. The menu shows `appliedUiLanguage()` (the choice actually in use: `'auto'` when the chosen catalog failed to load), never a fresh storage read, and a refused write shows `languageSaveFailedMessage(err)` (Chrome's reason only through `knownErrorText()`, else `settingsSaveFailedPlain`). `followUiLanguageChanges()` (registered by `index.tsx`) reloads the page when the stored choice changes to one it is not in, from another window or device (`uiLanguageChangeNeedsReload()`, pure). Each endonym option carries its code as `lang` (`SelectOption.lang` in `src/components/select-menu.tsx`) so a screen reader reads it in that language. The worker starts the read at load and every text-making handler waits on `uiLanguageReady()` (see the service-worker table); a change of the setting re-registers the context menus. Out of reach: the manifest's name, description, `action.default_title` and the command descriptions at chrome://extensions are read by Chrome itself and always follow Chrome's language.

**Where messages live.** `public/_locales/<lang>/messages.json`, copied as it is to the extension root, where Chrome looks. Each entry is `{ "message", "description" }`: the description tells a translator where the text appears, what each `$n` is and any length limit (button, menu item, the 132-character Summary). The manifest refers to messages instead of holding text: `name: '__MSG_extName__'`, `description: '__MSG_extDescription__'`, `action.default_title: '__MSG_actionTitle__'` and each command's description (`__MSG_cmdSaveSession__`, ...), so Chrome, chrome://extensions and the Web Store show them in the user's language.

**Reading them: `src/lib/i18n.ts`.**

- `t(key, ...subs)` is `chrome.i18n.getMessage` with `$1`..`$9` filled in, or the same lookup in the chosen language's catalog (below). `MessageKey` is typed from the English file, so a missing key is a type error.
- `tp(base, count, ...extra)` is a counted phrase: keys `<base>_one` / `<base>_other`, chosen with `Intl.PluralRules` for `uiLocale()`, `_other` as the fallback; `$1` is the count formatted for the language, `$2`.. are `extra`. Korean and Japanese need only `_other`. Spanish rules also return `many` (for a million and up); no Spanish `_many` key is shipped, so those counts read the `_other` form, which is correct Spanish for numerals. A language may add `_many` (or `_few`, ...) keys when its plural rules need them, and the parity test accepts them as long as the English `_other` exists. Every counted phrase goes through `tp()`, never `count === 1 ? ... : ...`.
- `uiLocale()` is the language the text is actually shown in: the `localeCode` message (`en`, `es`, `ko`, `ja`; its description says not to translate it), not `chrome.i18n.getUILanguage()`. For a Chrome language the extension does not ship (French, Portuguese, ...) Chrome falls back to the English messages, so `localeCode` reads `en` and plurals and number formats are English too, matching the text (a French Chrome sees "0 tabs" and "1,234", never "0 tab" or "1 234"). Every `Intl.*` call that formats something a person reads takes `uiLocale()` (`formatNumber(n)`, `new Intl.DateTimeFormat(uiLocale(), ...)`), never `toLocaleString()` without a locale and never an English month name. `src/pages/index.tsx` sets `document.documentElement.lang = uiLocale()` at startup.
- `joinSentences(a, b, ...)` puts complete sentences side by side through `commonSentenceJoin` (`$1 $2`; `$1$2` in Japanese, which puts no space between sentences), and `joinFacts([...])` separates short facts on one line through `commonFactJoin` (`$1 · $2`). Only for whole sentences and independent facts; a sentence is never assembled from fragments (see Message rules).
- `t()` needs `chrome` at run time and the tests switch language, so a module-level constant never holds user text: make it a function or compute it at the call. The service worker may call `t()` inside its handlers (`chrome.i18n` works there).

**Message rules.** Key names are camelCase `[A-Za-z0-9_]` with an area prefix (`settingsSortBy`, `storageDeleteAllTitle`); reuse the shared keys (`extName`, `extDescription`, `actionTitle`, `cmd*`, `assembleName`, `common*` such as `commonLoading`, `commonCopiedLinks_*`, `commonWindowsAndTabs`, `tabCount_*`, `windowCount_*`, `sessionGone`) rather than adding a second key with the same English in the same role. One term per concept per language: memos (the free-form page) are Memos / Apuntes / 자유 메모 / 自由メモ and YouTube notes are YouTube notes / Notas de YouTube / YouTube 메모 / YouTube メモ, because Korean and Japanese already call notes 메모 / メモ; the passphrase is the sync passphrase / frase de contraseña de sincronización / 동기화 암호 문구 / 同期パスフレーズ; the automatic snapshots are "snapshots" everywhere in English (sidebar heading, search group and toggle, Settings, storage hints, notices), instantáneas in Spanish, 스냅샷 in Korean, スナップショット in Japanese; a message that names a setting quotes that setting's own label (`storageSnapshotHint` quotes `settingsKeepLast`); a session name is quoted the same way within a language (“$1” in English, «$1» in Spanish, “$1” in Korean, 「$1」 in Japanese). One key per whole sentence, with substitutions written in the message (`$1`, a literal dollar sign `$$`): never build a sentence by concatenating translated pieces or by putting a translated word into another sentence, because word order differs between languages. No em dash (U+2014) or en dash (U+2013) in any language; write `-`.

**Stock shadcn text.** `src/components/ui/` stays as the CLI wrote it, and its only built-in English is the dialog's × (a screen-reader "Close"): every `DialogContent` passes `showCloseButton={false}` and renders `DialogCloseButton` (`src/components/dialog-close-button.tsx`, same look and place, `aria-label={t('commonClose')}`) as its last child. `DialogFooter`'s optional Close button stays unused.

**Never translated, and why.**

- Storage keys, ids, route names (`#saved/<id>`), CSS classes, data attributes: code reads them back.
- `console.*` text and errors that are only logged: they are for developers and bug reports.
- Error messages thrown by our own code (`new RangeError('No window at index 3')`) and Chrome's own error text: they stay English for the console, and are never shown as they are. `src/lib/error-message.ts` is the one way an error reaches the page: `errorMessage(err)` / `reportError(context, err)` (logs the original, returns the text to show) map what can be explained (`LocalizedError`, whose message was made with `t()`; `ExplainedError`, an English message plus a `userKey`; `UnknownSchemaVersionError`, `MalformedRecordError`, our index `RangeError`s, quota, `NotAllowedError`, Chrome's "cannot be edited", "No tab with id" and bounds errors) to `error*` messages, and everything else to `errorGeneric`. `knownErrorText(err)` returns `undefined` for the rest, so a line that embeds a reason (`expCopyFailed`, `restoreFailedItem`, ...) uses its `*Plain` variant instead of English. `errorDetail(err)` is the original, for `console.*`.
- Machine formats: the CSV header (`CSV_HEADER`) and JSON field names, so a file opens the same everywhere.
- Every token the importer parses back, such as `(pinned)` in text exports and the Netscape HTML structure: an export made in one language must import in another, byte for byte. Only the human-readable parts of Markdown/Text/HTML exports (headings, "Window N" labels) are translated.
- Text already stored: a session or snapshot name is created in the UI language at that moment and then kept as it was saved; switching Chrome's language, or the one chosen in Settings, does not rename it.

**Adding a key.** Add it to `en/messages.json` with a description, then to `es`, `ko` and `ja`, in that order, with the same `$n` (a language may reorder them); use it through `t()` / `tp()`. **Adding a language.** Add the code to `SUPPORTED_LOCALES` in `src/constants.ts` (the one list: the Settings menu, `src/tests/i18n.test.ts`, `LISTING_LOCALES` in `scripts/store-listing.ts`, the scripts and the website's languages in `site/` all derive from it) and add `public/_locales/<code>/messages.json` with every English key. The type checker then names what still lacks it: its endonym in `LOCALE_ENDONYMS` (`src/constants.ts`), its English name in `LOCALE_NAMES` (`scripts/store-listing.ts`), `POSIX_LOCALES` in `scripts/e2e/browser.ts`, `FIXTURE_TEXT` in `scripts/prepare-registration.ts`, and the site's `OG_LOCALES` and copy (`site/src/i18n/`, plus `site/src/privacy/<code>.md`). Then add its Description to `STORE_DESCRIPTIONS` in `scripts/store-listing.ts`, and add it to README's language list.

**What guards it.** `src/tests/i18n.test.ts`: exactly the shipped folders; every language has every English key and nothing else (plural forms aside), the same `$n`, no empty message, no long dash; every English entry has a description and a Chrome-valid name; every `_one`/`_many` has its `_other`; every file's `localeCode` names its own language. `src/tests/chrome-fake.ts` implements `chrome.i18n` by reading `public/_locales` (`getMessage` with substitutions and Chrome's per-key fallback to English, `getUILanguage`), English by default, and `setUiLanguage(code)` switches a test to another language (`'fr'` for one that is not shipped), so tests compare real English output and can check another language. `readLocaleFile(code)` is the catalog reader tests pass to `applyUiLanguage()`, and `fetchPackagedFile` (installed with `vi.stubGlobal('fetch', ...)`) serves the same files at the fake's `chrome.runtime.getURL()` addresses for code that uses the default reader (the worker). `src/tests/i18n.test.ts` checks that, for every key of every language, the override returns exactly what the fake's `getMessage` returns in that language, and that after the named placeholders are expanded every `$` in every message is `$$` or `$1`..`$9` (real Chrome drops an invalid `$x`, `$0` or a trailing lone `$`, which the override and the fake keep, so no message may contain one); `src/tests/ui-language.test.ts` covers the stored setting. `src/tests/store-listing.test.ts`: every language's store Description and Summary (below).

**The Web Store listing.** `scripts/store-listing.ts` holds, at its top, everything typed into the dashboard: `STORE_DESCRIPTIONS` (one plain-text Description per language, pasted as it is: no Markdown, no long dash, at most 500 characters, the owner's limit; details go to the website and README), the product details, the privacy answers and the reviewers' test instructions, all other text in English. Quoted menu items and buttons use that language's `messages.json` wording (the test checks `assembleName` in each Description and every quoted label in `TEST_INSTRUCTIONS`), and a change to the English Description reaches the three translations in the same edit. Title and Summary are not copied anywhere: the store reads them from the package (`extName` / `extDescription`, Summary at most 132). `src/tests/store-listing.test.ts` checks all of it. `pnpm store:bundle` writes it into `release/store-<version>/SUBMIT.md` with `screenshots/<code>/` folders (a language without its own shows the English ones). `LOCALES=en,es,ko,ja pnpm exec tsx scripts/prepare-registration.ts` shoots the screenshots per language (headless by default: Playwright's `chromium` channel, since the default headless shell cannot load an extension; it builds into `node_modules/.cache/tabinet/store-screenshots/`, never `dist/`, in the `store-screenshots` mode, where Settings shows Google sign-in as the store build does).

## Sync server

`server/` is the cloud sync backend: its own workspace package `tabinet-server`, deployed as a Vercel project whose root is `server/` (functions in Singapore `sin1`), with Postgres on Neon (`aws-ap-southeast-1`; the region is stated in `PRIVACY_POLICY.md`, so a move updates it), live at `https://tabinet-server.vercel.app`. `server/README.md` has the API, the formats by reference to the spec, the environment, the key encryption key commands, rotation and loss, the migration flag and Railway.

- **End-to-end encrypted.** Per record the server stores `{ kind, id, updated_at, deleted, iv, ciphertext, seq, stored_bytes }` (`kind`: `session`, `settings`, `image` or `doc`; a doc's id is an opaque HMAC, so a memo and a note look alike apart from size) and never sees a name, url, title, note, video id or picture. Per account: email, Google `sub`, the sealed key envelope with its `keyId`, `generation` and `key_encryption_key_id`, the `write_verifier`, `last_seq` and the usage counters. Bearer tokens are 32 random bytes, kept only as their SHA-256, valid `POLICY.signIn.tokenLifetimeMs`.
- **The key encryption key.** `TABINET_KEY_ENCRYPTION_KEY` (b64 of 32 bytes, Vercel Production only, never in a file) seals each envelope under AES-GCM with `["tabinet-envelope-v2", sub, keyEncryptionKeyId, keyId, generation]` as AAD (`server/src/envelope.ts`: `seal()`, `open()`, `parseEnvelope()`, `envelopeBytes()`), so the database alone holds nothing to test a passphrase against. It is opened only with the `sub` of a Google answer verified in that same request, never one read from SQL; any failure, or a row under another key encryption key, is 500 `key_unavailable` and writes nothing. `server/src/key-encryption-key-id.ts` pins `PINNED_KEY_ENCRYPTION_KEY_ID`; `pnpm --filter tabinet-server key-encryption-key:new <absolute path outside the repository>` writes a new key encryption key and prints only its id, `key-encryption-key:id` prints the id of one. Rotation and loss are one procedure: new key encryption key, replace `TABINET_KEY_ENCRYPTION_KEY` and `PINNED_KEY_ENCRYPTION_KEY_ID` together, deploy, then change the passphrase on a ready device (the PUT reseals); until then a new device's Unlock gets `key_unavailable`. No keyring, no reseal script.
- **Fails closed.** `readEnv()` in `server/src/env.ts` checks, unconditionally and in this order, `VERCEL_ENV === 'production'`, a non-empty pin, and a `TABINET_KEY_ENCRYPTION_KEY` whose id is the pin, before anything else; `createServer()` (`server/src/production.ts`) answers every request, `/v1` and OPTIONS included, 500 `internal` with zero queries when it throws. So a preview deployment (it shares the database: preview is **not** separated, and pushed code can still delete or roll back rows, though never open an envelope) and a production deployment with a wrong key encryption key refuse to run, and deployments built before v10 fail on the renamed tables (`accounts`, `account_tokens`, `account_records`, `apply_account_record()`; `server/src/tests/fail-closed.test.ts`). Railway (`server/src/railway.adaptor.ts`) is code only and refuses to run for the same reason. `server/src/dev.ts` (127.0.0.1, in-memory PGlite, a random in-memory KEY_ENCRYPTION_KEY) never calls `readEnv()` and can never reach production.
- **Routes** (`createApp(deps)` in `server/src/app.ts` reads top to bottom as the whole API; handlers in `server/src/routes/`, middleware in `server/src/middleware/`, every SQL statement in `server/src/db/store.ts`). `POST /v2/auth/google` `{ accessToken }` → `{ token, expiresAt, accountId, email, key }`; `POST /v2/auth/logout`; `GET /v2/me` → `{ accountId, email, key, usage }`; `POST /v2/keys/open` `{ accessToken }` → `{ envelope }`; `PUT /v2/keys` `{ accessToken, envelope, proof }` (201 create, 200 replace: same keyId, the proof, generation + 1, one conditional UPDATE); `GET /v2/records?since=` (NDJSON, `server/src/stream.ts`); `POST /v2/records` `{ records }` → `{ results, usage }`; `DELETE /v2/account` `{ accessToken }` (bearers and records cascade). The key routes and the deletion check Google again and require the verified `sub` to be the bearer's account (403 `google_account_mismatch` otherwise); Google refusing is 403 `google_refused`, Google unreachable (timeout, network, 408, 429, 5xx) 503 `google_unavailable`, never a false 401. The record routes need `Tabinet-Key-Id` equal to the account's key (409 `key_missing` / `key_mismatch`, decided before the body is read). `/v1` and `/v1/*` answer 410 `upgrade_required` before bearer, body and database (`server/src/middleware/v1-gate.ts`).
- **The HTTP contract is fixed** (`server/src/tests/contract.test.ts`). Order: CORS and OPTIONS, the `/v1` gate, route match (404, 405 with `Allow`), bearer (401, and 401 means nothing but the bearer), key header, body, Google, database. JSON answers carry `Cache-Control: no-store`, errors are exactly `{ "error": "<code>" }`, CORS headers are on errors too, a path matches on the exact `URL.pathname`, a trailing slash is 404, HEAD is not a GET, any OPTIONS is 204. **Query parameters that are not named are ignored**: Vercel's rewrite of `/v2/:path*` appends `path=<value>` to the query. Bodies are read as a stream by `readJsonBody(limit)` (`server/src/middleware/body-limit.ts`): reading stops at the first chunk over the limit (413), whatever Content-Length says, and the rest is drained, never cancelled and never buffered; `maxSmallBodyBytes` on auth, keys and account, `maxBodyBytes` on records. Answers are built by `server/src/responses.ts`, not `c.json()`.
- **Writes** (`apply_account_record()`, migration `003_sync_v2.sql`, one call per record in request order, each under the account row lock so an account's `seq` order is its commit order): `clock_ahead` beyond `maxClockAheadMs`, decided before SQL; session, settings and image apply only over an older `updatedAt`; a doc applies only when `baseSeq` equals the stored seq (null: no row) **and** `updatedAt` is greater (compare and swap). `stored_bytes = max(ciphertext, maxTombstoneChars) + overheadBytes`. A live write that would grow the account past `POLICY.account.storageBytes` (50 MiB, a hard bound) or add a screenshot past `POLICY.account.screenshots` is `rejected`; a shrinking write passes; a tombstone over an existing row always applies; a tombstone for a row the server lacks is written when it fits and answered `absent` (nothing stored) when it does not. Stale answers carry `current` up to `maxStaleBytes` in all, then `withheld: true`.
- **The stream** (`GET /v2/records`): `through` (the account's `last_seq`) and usage are read first; then a `ReadableStream` with `highWaterMark: 0` runs one database batch per `pull()` (at most `batchRecords` and `batchBytes` of `stored_bytes`, at least one row), each followed by a checkpoint; `end` with `complete: true` when a batch is empty, `complete: false` once `streamMs` passed. A throw, a timeout, a deleted account or a changed key closes the stream **without** an end line and logs the error's name only (never `controller.error()`, which the Node adaptor would log whole). `cancel()` stops the queries.
- **Entry points.** Production is `server/api/vercel.adaptor.ts` (the only Vercel-specific code; it stays in `api/` with `"framework": null` pinned in `server/vercel.json`, which also rewrites `/v1/*` and `/v2/*` to it and installs with `pnpm install --frozen-lockfile --filter tabinet-server --ignore-scripts`); Railway is `server/src/railway.adaptor.ts`; local is `pnpm --filter tabinet-server dev`. The owner's names `vercel.adaptor.ts` and `railway.adaptor.ts` stay as they are.
- **Static output.** `server/public/` (only `robots.txt`) is the only directory Vercel serves as static files. Never delete it: with the preset Other and no `public/`, Vercel serves the whole project directory.
- **Migrations** are plain SQL, `server/migrations/NNN_name.sql`, applied once each by `pnpm --filter tabinet-server migrate` (recorded in `schema_migrations`). `003_sync_v2.sql` deletes every v1 account and refuses to run on a database with v1 users unless `WIPE_V1=yes`; `schema:check` prints applied migrations, table names and row counts (SELECTs only, never a row or the URL); `stream-check` checks a deployed stream. Never edit a shipped migration; add the next number. Never run a migration from an agent session against a real database.
- **Tests** are `server/src/tests/*.test.ts`, run by `pnpm server:test` against PGlite with the real migrations; the concurrency tests need a real Postgres (`TEST_DATABASE_URL`, localhost only; CI's `postgres:17` service) and are skipped without it. `pnpm server:typecheck` uses the package's own `tsconfig.json` (`NodeNext`, relative imports end in `.js`). The root vitest excludes `server/**`, except that the extension's contract suite imports `server/src/app` and the db modules directly.
- **Environment** (`server/.env.example` lists every key): `DATABASE_URL`, `GOOGLE_CLIENT_IDS`, `ALLOWED_ORIGINS` (e.g. `chrome-extension://bmbpmnfhfbdjdjpblimidmbohgccmjdg`), `TABINET_KEY_ENCRYPTION_KEY` (production only), `VERCEL_ENV` (set by Vercel). Logs carry an error's name only, never a token, envelope, proof, ciphertext or connection string. `server/` pins TypeScript 6: Vercel compiles the function with the project's own `typescript`.

## CI/CD

### GitHub Actions (`ci.yml`)

Runs on push to `main`, PRs to `main`, and manual dispatch:

1. Setup mise tools (`jdx/mise-action`; installs Node, pnpm, lefthook and gitleaks from `mise.toml`; the checkout fetches the full history - no Node version matrix)
2. Restore the pnpm store cache (keyed on `pnpm-lock.yaml`)
3. `gitleaks git` over every commit (fails on any finding; config `.gitleaks.toml`)
4. `pnpm install --frozen-lockfile`
5. `pnpm typecheck`
6. `pnpm test` (vitest over the extension; includes `src/tests/store-listing.test.ts`, which fails on a store description over 500 characters, a summary over 132 or a permission without a justification, and `src/tests/i18n.test.ts`, which fails when the `_locales` drift apart)
7. `pnpm server:typecheck` and `pnpm server:test` (the sync server, `server/`; its tests run against PGlite, no database needed)
8. `pnpm format:check` (oxfmt; fails when any file is not formatted)
9. `pnpm lint` (oxlint; fails on any warning or error)
10. `pnpm build`
11. `pnpm site:build` (the project website; `astro check` fails on any type error)

Dependabot (`dependabot.yml`) opens weekly PRs for npm and GitHub Actions updates, grouping minor/patch bumps. They no longer merge by themselves (the auto-merge workflow is gone since v10): `main` deploys next to the server's key encryption key, so the owner merges every dependency update. `ci.yml` runs a `postgres:17` service and passes `TEST_DATABASE_URL` to `pnpm server:test`, for the server's concurrency tests on real Postgres.

### Website (`pages.yml`)

Builds `site/` with `pnpm site:build` and deploys `site/dist` to GitHub Pages (`actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`; concurrency group `pages`). Runs on a push to `main` that touches `site/**`, `assets/**`, `public/img/**`, `PRIVACY_POLICY.md`, `package.json` (the version the support page shows), the lockfile, `pnpm-workspace.yaml`, `mise.toml` or the workflow itself, and on manual dispatch. The repository's Pages source must be "GitHub Actions" (Settings > Pages).

### CodeQL (`codeql.yml`)

Security scanning for JavaScript/TypeScript on every push and pull request to main, and weekly (Sundays at 20:00 UTC).

### Release procedure (Chrome Web Store)

`pnpm release` runs release-it (`.release-it.json`): `before:bump` executes `scripts/prepare-registration.ts` (build, Settings + the five `assets/en/dashboard-*.png` captures (sessions, restore, YouTube notes, search, snapshots; fixture sessions and notes from `scripts/e2e/fixtures.ts`), promo tiles), then the version is bumped, `after:bump` runs `pnpm build` + `scripts/zip.ts` (→ `release/Tabinet-<version>.zip`, named from `package.json` `displayName`) + `scripts/store-bundle.ts` (→ `release/store-<version>/`, whose `SUBMIT.md` carries every text from `scripts/store-listing.ts`), and a GitHub release is created. It requires the `main` branch and hooks/CI green. Every optional step of `prepare-registration.ts` is skippable on its own (`SKIP_BUILD`, `SKIP_OPTIONS`, `SKIP_DASHBOARD`, `SKIP_PROMO`), so one asset can be regenerated without a full run; `pnpm exec tsx scripts/zip.ts` packages an existing `dist/` on its own.

1. Release through a pull request like any change: on a `release/vX.Y.Z` branch regenerate whatever store assets changed (`tsx scripts/prepare-registration.ts` with the `SKIP_*` flags for the rest), set the version with `npm version X.Y.Z --no-git-tag-version`, and open a `chore: release vX.Y.Z` pull request. Before merging it, make sure `scripts/store-listing.ts`, `PRIVACY_POLICY.md` (Last Updated), `README.md` and this file describe what ships, and that `package.json` `description` (the store Summary) is ≤ 132 characters.
2. After the merge, on an up-to-date `main`: `pnpm release --ci --no-increment --no-git.commit` with every `SKIP_*` flag set (the assets are already committed). release-it then only builds, zips, writes `release/store-<version>/`, and pushes the `vX.Y.Z` tag; nothing is committed to `main`. If it prints a "releases/new" link instead of creating the GitHub release (no `GITHUB_TOKEN`), create it with `gh release create vX.Y.Z --title vX.Y.Z --notes …`.
3. In the CWS Developer Dashboard, follow `release/store-<version>/SUBMIT.md`: the zip, each language's Description and screenshots, the promo tiles, the Privacy answers (re-review the data-type rows), the Test instructions and Distribution.
4. Submit for review. Never run `pnpm release` from a feature branch or a worktree.

## Testing

Unit tests use **Vitest** and always live inside `src/`, in each package's `src/tests/` (the server's in `server/src/tests/`). The extension's live in `src/tests/`, flat, one `<module>.test.ts` per module (never next to the source); the root `tsconfig.json` leaves that folder out and `src/tests/tsconfig.json` checks it. `src/tests/tsconfig.json` type-checks them with Node types added, so a test may use `fs` / `path` while `src/` may not; `pnpm typecheck` is `tsc --noEmit && tsc --noEmit -p src/tests`. Pure sorting logic in `src/lib/sort-order.ts` is tested in `src/tests/sort-order.test.ts`, covering:

- `urlSortKey` - hostname normalization (`www.` stripping), pathname/search/hash ordering, special schemes (`chrome://`, `chrome-extension://`, `file://`, `about:blank`)
- `extractGroupingKey` - subdomain vs domain mode, two-part TLDs (`co.uk`, `ac.kr`, `com.au`)
- `isSuspended` / `tabToUrl` - suspended tab detection and URL extraction
- `findDuplicateTabs` - duplicate detection, `pendingUrl` fallback, special scheme handling
- `sortByTitleOrUrl` - title/URL sorting, pinned tab exclusion, edge cases (empty arrays, mixed schemes, large diverse tab sets)

`vite.config.ts` sets `test.setupFiles: ['src/tests/setup.ts']`, which installs `createChromeFake()` from `src/tests/chrome-fake.ts` on `globalThis.chrome` before every test (typed against `@types/chrome`, no `any`) and a `navigator.locks` shim. Tests reach the fake through `getChromeFake()`: `state`, `fire.installed/startup/menuClicked/command/alarm/actionClicked/tabReplaced`, `failNext(api, n, message)` (`tabs.create`, `tabs.group`, `tabs.move`, `tabGroups.move`, `windows.create`, `storage.local.set`, `scripting.executeScript`) and `commitNavigation(tabId)` (`state.deferCommit` models a navigation that has not committed). The `chrome.tabs`/`chrome.windows`/`chrome.tabGroups` `on*` events are emitted by the fake's own mutations - creating, moving, grouping or closing a tab fires them, which is what `useOpenWindows` is tested against - so only `actionClicked` (the second `action.onClicked` listener) and `tabReplaced` (no mutation produces it) need `fire.*` helpers of their own. Moves between windows follow real Chrome, pinned in `chrome-fake.test.ts`: a cross-window `tabs.move` drops `pinned`, leaves the group, arrives inactive and closes an emptied source window; `tabGroups.move` carries the members and group properties, and carries the source's active tab (expanding the group) when it holds it; activating a tab inside a collapsed group expands it; `tabs.ungroup` of a group's middle tab moves it just after the group (expanding a collapsed group when it is the active tab); `windows.create` honours `type` and `incognito`. `tabs.query({ url })` reads Chrome match patterns (a `*.` host also matches the bare domain). `chrome.permissions` keeps host grants in `state.grantedOrigins` (empty at install), refuses to request anything not in `state.optionalOrigins` and answers prompts with `state.permissionAnswer`; `onAdded`/`onRemoved` fire only on a real change. `chrome.scripting.executeScript` rejects a missing or discarded tab and a host that was not granted, rebuilds `func` from its source text (so a function leaning on an import or closure fails as it would in Chrome) and runs it against a fake `document` whose media elements are `state.pageMedia` (`fakeMedia()`, with `videoWidth` / `videoHeight` / `readyState` and `tainted` for screenshots) and whose `createElement('canvas')` gives a canvas recorded in `state.pageCanvases` (`toDataURL` throws a `SecurityError` once a tainted element was drawn); `state.injectedTabs` records where it ran. `chrome.identity.getAuthToken` answers with `state.authTokenAnswer` (a token, an `Error`, or a function of the request) and records each request in `state.authTokenRequests`; `removeCachedAuthToken` is recorded in `state.removedAuthTokens` and `clearAllCachedAuthTokens` counted in `state.authTokenCacheClears`. `chrome.sidePanel.open` needs an existing window or tab and records each call in `state.sidePanelOpens` (the user gesture is not modelled, so a test checks the call happened synchronously in the event); `state.sidePanelBehavior` is `openPanelOnActionClick: false`. `fire.menuClicked` / `fire.command` hand over the focused window's active tab, as Chrome does. Fake media elements carry `duration` (NaN until set) and `play()`, and the fake page's `document.title` is the tab's title. Do not relax these - `src/tests/assemble-tabs.test.ts` would pass falsely. Session tests are `src/tests/<module>.test.ts` for each session module of `src/lib/` (naming, migrate, hash, capture invariants, storage order/reconcile/lock/prune/protect, planner chunking and step order, executeRestore against the fake, history dedupe/prune/recovery promotion/alarm re-arm, search tokenising and ranking, export serializers incl. CSV quoting and HTML escaping, import detection/parsers/JSON round-trip, guards on malformed input, suspender unwrap) and `src/tests/service-worker.test.ts` (menus recreated on install, badge, handlers, alarm / second-click / `storage.onChanged` wiring). Page-side logic and hooks are tested in `src/tests/` too (`src/tests/<helper>.test.ts`, `src/tests/use-session-body.test.ts`, `src/tests/use-session-index.test.ts`, `src/tests/use-session-settings.test.ts`); React components themselves are not unit-tested (vitest runs in Node without a DOM; the one exception, `sync-status-field.test.ts`, checks server-rendered markup for the focus rule of Sync now) - keep decisions in pure helpers with tests and leave components thin.

**Testing a module that registers `chrome.*` listeners at import time** (`src/service-worker.ts`): `src/tests/setup.ts` assigns one throw-away fake to `globalThis.chrome` at module load (just so these modules are importable at all), then installs a **fresh** fake in `beforeEach`. A static `import '@/service-worker'` at the top of a test file runs once, before any `beforeEach`, and registers its listeners on the throw-away instance - every later `getChromeFake().fire.*` call reaches a different fake, so nothing fires. The fix is to defer the import into the test body, after `beforeEach` has installed that test's fake: `vi.resetModules(); await import('@/service-worker');`. `src/tests/service-worker.test.ts`'s `describe('listener wiring', …)` block does exactly this per test (`onInstalled`/`onStartup`/menu-click/command tests), and so does `src/tests/service-worker-sort.test.ts` for the icon click; the same file's other tests call the statically-imported `handleMenuOrCommand()`, `registerContextMenus()`, etc. directly, which is fine since those don't depend on which fake the listeners were registered against. (`src/tests/session-repo.test.ts` also calls `vi.resetModules()` before re-importing `@/lib/session-repo`, but for an unrelated reason - getting a fresh copy of that module's own `fallbackChain` state to test the no-`navigator.locks` code path in isolation, not a listener-registration issue.)

### Real-Chrome smoke test (committed)

`scripts/e2e/smoke.ts` is a committed end-to-end harness that loads the built extension into a real Chromium and drives the app page: build a fixture window (pinned tabs, a titled coloured group, a collapsed group) → Save → the session's own view → Open → rename → delete, verifying each result through `chrome.tabs`/`chrome.tabGroups` inside the extension's own service worker rather than through the UI it just clicked. 11 steps, about 3 s.

```bash
pnpm build && pnpm exec tsx scripts/e2e/smoke.ts
```

It runs under `tsx`, not vitest, so `pnpm test` does not include it - run it by hand after touching restore, capture or the worker's listeners. Steps run in order and a failure stops the run (the rest report `SKIP`); the process exits 1 if any step failed. Flags: `PW_CHROMIUM` (binary, default `/opt/pw-browsers/chromium`), `HEADLESS=0`, `SMOKE_TIMEOUT_MS`, `SMOKE_KEEP_OPEN=1`. `scripts/e2e/browser.ts` (`launchExtension()`) and `fixtures.ts` (sessions seeded straight into `chrome.storage.local`) are shared with `scripts/prepare-registration.ts`; `server.ts` (127.0.0.1 fixture pages - the QA browser has no outbound network) is used only by the e2e scripts (smoke, sort, selection, assemble). Extend it by appending a `Step` to `STEPS`; history, search, export and import are not covered yet.

Playwright itself is a devDependency, used by this harness and by `scripts/prepare-registration.ts` for the release screenshots and promo images. The manual CDP passes described below are what produced the `waitForCommit` and window-state fixes in `src/lib/session-restore.ts`.

### Real-Chrome assemble-tabs check (committed)

### Real-Chrome QA (manual, beyond what the smoke test covers)

Vitest + the chrome fake cannot catch Chrome's own argument validation or its navigation timing, and the smoke test only covers the save/restore/rename/delete path. For anything else - history, search, export, import, window states - drive a real Chrome for Testing build once. What was learned doing it:

- **Do not let Playwright launch the browser when the run can reach `chrome.tabs.discard`.** Its default Chromium launch flags make Chrome for Testing 151 **SIGSEGV on `chrome.tabs.discard`** (i.e. exactly the lazy-restore path). For that path, launch Chrome for Testing yourself with `--load-extension=<dist>` plus `--remote-debugging-port=<port>` (and a scratch `--user-data-dir`), then attach with `chromium.connectOverCDP('http://127.0.0.1:<port>')`. `scripts/e2e/browser.ts` does use `chromium.launchPersistentContext`, which is safe only because its fixture (6 tabs) stays at or below `POLICY.restore.lazyAboveTabs` (`src/constants.ts`) and so never discards a tab - keep it that way, or move that harness to CDP first.
- **Pick the right service worker.** Component extensions register service workers too, so `context.serviceWorkers()` has several entries. Select ours by its URL ending in `/service-worker-loader.js` - never by index - and `evaluate` the `chrome.*` calls inside it.
- **`--load-extension` is ignored by branded Chrome ≥ 137.** Use a Chrome for Testing binary (`npx @puppeteer/browsers install chrome@<version>`), not the installed Chrome.
- **Verified this way (do not "simplify" these back):** `chrome.windows.create` rejects `{ state: 'minimized', focused: true }`, `{ state: 'maximized' | 'fullscreen', focused: false }`, and any non-`'normal'` state combined with `left/top/width/height`, all with `Invalid value for state` - so restore always creates a `'normal'`, unfocused window and applies the real state afterwards with `windows.update`. And `chrome.tabs.discard` on a tab whose navigation has not committed silently unloads it with `url: ''`, losing the URL - hence `waitForCommit`. `src/tests/chrome-fake.ts` models both behaviours so the unit tests hold the line.

## Gotchas & Edge Cases

- **Vercel's rewrite adds a query parameter**: `/v2/:path*` reaches the function with `path=<value>` appended to the query, so the server ignores every query parameter it does not name. Never make a route reject unknown parameters.
- **A `null` in `chrome.storage.local` is absent**: one-write changes stage a deleted key as `null` and remove it afterwards; a crash in between leaves the `null`, which every reader and `reconcile()` treat as no value.

- **No `manifest.json` file**: The manifest is defined inline in `vite.config.ts`. Don't look for a separate manifest file.
- **Suspended tabs**: The extension recognises the pages of The Great Suspender's family (The Marvellous Suspender and its forks) by shape, whatever the extension id: `chrome-extension://<32 letters a-p>/suspended.html#ttl=…&pos=…&uri=<real-url>` with the real URL appended raw (not percent-encoded). There is no setting for the suspender's id. `isSuspendedUrl()` / `unwrapSuspendedUrl()` in `src/lib/suspended-url.ts` are the only code that knows the format: sorting (`isSuspended()` / `tabToUrl()` in `sort-order.ts`), capture, the open-windows pane and the restore sanitiser all call them. Unwrapping returns the verbatim remainder after `uri=` - parsing it with `URLSearchParams` would cut the URL at its first `&`. A page of our own extension is never treated as suspended. A wrapper that cannot be unwrapped keeps the raw wrapper URL at capture time and is skipped by `sanitizeRestoreUrl` (foreign `chrome-extension://`) at restore time.
- **Tab group IDs**: `-1` means ungrouped in the Chrome API. The code uses this convention throughout.
- **Tab ID arrays**: Chrome's `tabs.move()` and `tabs.group()` require `[number, ...number[]]` tuple type for non-empty arrays.
- **`scripts/zip.ts` and archiver 8**: archiver 8 is ESM and exports no callable default - the archive classes come by name (`import { ZipArchive } from 'archiver'`). `finalize()` resolves before the file is complete, so the script also waits for the write stream's `close` event; don't "simplify" either back.
- **`pnpm-workspace.yaml`**: Lists two workspace packages, `site` (the project website) and `server` (the sync server); the extension is the root package. It also holds pnpm's install policy: `allowBuilds` (only `esbuild` may run install scripts) and `minimumReleaseAge: 10080` (minutes - only versions published at least 7 days ago are installed; pnpm's default is 1 day). A lockfile entry younger than that makes `pnpm install --frozen-lockfile` fail, in CI too, so `dependabot.yml` carries the matching `cooldown: default-days: 7` for npm. `minimumReleaseAgeExclude` is the escape hatch (exact `name@version`) for a release that must be installed sooner; there is none at the moment.
- **The store text is data, pasted by hand**: `scripts/store-listing.ts` is the only source of the dashboard text; only Title and Summary come from the package (`_locales`).
- **No Python** (set by the owner): every script is TypeScript run with `tsx`; no `.py` file, virtualenv, ruff or pip config in this repository.
- **Pre-push `update-docs` hook amends commits**: on feature branches push with `LEFTHOOK_EXCLUDE=update-docs git push …` and do one manual docs pass per phase.
- **`chrome.tabs.Tab.id` and `chrome.windows.Window.id/state/type/left/top/width/height` are optional** in `@types/chrome` 0.3.x - always narrow before use; never `!`. `Tab.windowId`/`groupId` are required (`-1` = no group).
- **`chrome.storage.local.getKeys()`** needs Chrome 130+; only `reconcile()` uses it, behind a `typeof … === 'function'` guard.
- **App-page singleton**: the sorter still moves/dedupes the app tab like any tab; `openDashboard()` focusing an existing tab is what keeps "close duplicates" harmless. It matches `app.html*`, so it finds the tab whatever view its hash points at.
- **Alarms do not survive an extension update or reload**: `ensureHistoryAlarm()` re-asserts the periodic alarm from `onInstalled` and `onStartup` (`alarms.create` with an existing name replaces it, no churn). If `historyEnabled` is true and `chrome.alarms.getAll()` in the worker console shows nothing, history has silently stopped - that is the first thing to check.
- **The first post-launch snapshot is delayed on purpose**: `onStartup` arms the one-shot `history-first` alarm 1 minute out because Chrome is still restoring tabs while `onStartup` runs; a capture then would record half-loaded windows.
- **`promoteRecoveredSnapshot()` is idempotent**: only snapshots captured _after_ the newest existing recovered one qualify, so a restart with no new snapshot in between never turns another ring entry into a protected one.
- **History dedupe hashes URLs, not titles**: `contentHash()` covers url/pinned/groupIndex/group title, so a page changing its `<title>` never produces a new snapshot; deleting the snapshot that `historyMeta.lastHash` points at also drops `historyMeta`, otherwise the next capture of that layout would be skipped forever.
- **Import never trusts input**: everything pasted or uploaded goes through `src/lib/import-guards.ts`; imported sessions get fresh ids, `kind: 'saved'`, `origin: 'import'` and never keep `protected`. Netscape HTML is parsed with the module's own tokenizer - `DOMParser` is unavailable under vitest (Node, no DOM).
- **Open-windows pane listeners live in the page**: `useOpenWindows` registers `chrome.tabs/windows/tabGroups.on*` in `app.html` and coalesces refetches; `windowId`/`tabId` in `SearchEntry` for open tabs are in-memory only and are never written to storage.
